# E12-X1.8 — Implementazione livestock-first verificabile

Stiamo continuando il progetto Kaggriculture dalla diagnosi **E12-X1.7** appena completata.

La diagnosi X1.7 è APPROVATA.

## Decisione

E12-X1.7 deve essere considerata **architetturalmente non valida** come test dell'ipotesi livestock-first.

Non vogliamo correggere incrementalmente X1.7 né ottimizzarne i parametri.

Implementiamo invece **E12-X1.8** come prima versione realmente verificabile della seguente architettura:

> **livestock inner core → crop outer rings → controlled expansion**

L'obiettivo di questa iterazione NON è massimizzare immediatamente il denaro finale.

L'obiettivo primario è dimostrare che l'agente realizza fisicamente e mantiene nel game state questa struttura:

1. core centrale 2×2 dedicato permanentemente al livestock;
2. Cow #1 sostenibile e nutrita;
3. colture soltanto all'esterno del core;
4. crescita progressiva del numero di cow;
5. espansione agricola concentrica e controllata;
6. nessuna espansione territoriale prematura.

# 2. Correzioni preliminari obbligatorie

Prima della nuova architettura correggi o isola almeno questi errori già identificati.

## 2.1 Crop harvest readiness

La readiness non deve dipendere da fallback arbitrari tipo:

```python
growth_days = 3
```

quando tali campi non esistono nei wrapper correnti.

Usa esclusivamente le proprietà realmente esposte dal motore/wrapper, coerentemente con:

- `first_yield_day`
- `max_yield_day`

o con l'equivalente effettivamente disponibile.

Aggiungi test specifici.

---

## 2.2 Land cost

Elimina ogni assunzione:

```python
land_cost = 1000
```

generalizzata.

Il motore usa prezzi differenti:

- 1000
- 2000
- 4000

La logica deve utilizzare il prezzo reale della parcella/quadrante che si intende acquistare.

---

## 2.3 Crop worker capacity

La capacità agricola NON deve contare automaticamente tutti gli active workers.

Distingui esplicitamente almeno:

- livestock primary worker;
- crop workers;
- eventuali temporary Hands.

Il Farmer impegnato nel livestock non deve aumentare artificialmente la capacità crop.

La capacità coltivabile deve essere derivata dai **crop workers realmente disponibili**.

Mantieni per ora la regola esistente di circa:

```text
4 active crop tiles per crop worker
```

come limite prudenziale, salvo prova meccanica contraria.

# 4. CORE_BUILDING

Definisci quattro tile centrali contigue come **livestock core 2×2 permanente**.

Questi tile:

- devono appartenere a Q1/NW iniziale;
- non devono mai essere coltivati;
- non devono essere inclusi nei crop candidates;
- devono restare riservati permanentemente a pasture/animals.

Durante `CORE_BUILDING`:

1. costruisci le quattro pasture;
2. non avviare ancora la normale espansione crop;
3. non comprare land;
4. non fare workforce scaling aggressivo.

Il core non è completo con:

```text
pasture_count >= 1
```

ma esclusivamente quando:

```text
tutti e 4 i core tile sono pasture valide
```

---

# 5. FIRST_COW_BOOTSTRAP

Dopo il completamento fisico del 2×2:

1. compra Cow #1;
2. posizionala su una pasture del core;
3. registra/verifica la presenza dell'animale nel game state.

La semplice emissione di `BUY_ANIMAL` non equivale a Cow attiva.

Non comprare Cow #2 immediatamente.

---

# 6. FEED_STABILIZATION

Questo è il gate più importante di X1.8.

La Cow #1 deve sopravvivere attraverso un **feed loop realmente funzionante**.

Non definire `FEED_STABLE` semplicemente come:

```text
wheat_available > 0
```

o come acquisto di Wheat.

Serve evidenza di un ciclo operativo sostenibile.

## Obiettivo minimo

Entro Day 10:

- Cow #1 non deve essere scappata;
- deve essere stata nutrita quando necessario;
- deve esistere Wheat disponibile tramite produzione/inventario compatibile con il ciclo di feeding.

Implementa il minimo crop bootstrap necessario a produrre Wheat **fuori dal 2×2 livestock core**.

Il Wheat destinato all'alimentazione ha priorità sulle cash crops fino alla stabilizzazione della Cow #1.

Non avviare ancora l'espansione agricola generale.

---

# 7. CROP_BOOTSTRAP

Solo dopo che Cow #1 ha superato il gate di stabilizzazione:

- abilita colture esterne al core;
- mantieni geometria concentrica;
- usa inizialmente un working radius ridotto attorno al centro.

Obiettivo geometrico iniziale:

```text
core livestock 2×2
+
prima corona crop circostante
```

Non vogliamo dispersione verso i bordi del quadrante.

Preferisci sempre tile vicini al core rispetto a tile lontani equivalenti.

---

# 8. LIVESTOCK_SCALING

Le Cow devono crescere progressivamente:

```text
Cow #1 → Cow #2 → Cow #3 → Cow #4
```

Non comprare tutte le cow appena il cash lo permette.

Per ogni nuova Cow deve esistere un gate di sostenibilità.

Come minimo:

- Cow precedente ancora viva;
- feed loop funzionante;
- pasture libera disponibile;
- riserva Wheat sufficiente;
- capacità operativa sufficiente.

Preferibilmente, usa anche una prova produttiva:

- Cow precedente sopravvissuta abbastanza a lungo da entrare nel ciclo di milk production,

oppure una condizione equivalente verificata direttamente nel motore.

L'obiettivo finale del core è:

```text
4 pasture
4 cow
```

non:

```text
4 pasture
1 cow
```

---

# 9. Crop geometry

La crescita crop deve seguire una geometria **centered**.

Priorità spaziale:

1. livestock core centrale;
2. ring crop immediatamente circostante;
3. espansione progressiva verso un working area circa 5×5;
4. solo successivamente espansione ulteriore.

Non scegliere tile lontani semplicemente perché unlocked.

Separare chiaramente:

```text
owned/unlocked land
```

da:

```text
active working set
```

Il fatto che un tile sia posseduto non significa che debba essere immediatamente coltivato.

---

# 10. Weeds

Le weeds devono essere considerate parte del capacity problem.

Nel working set attivo:

- identifica weed;
- assegna priorità alla loro rimozione quando interferiscono con l'area produttiva;
- evita di espandere il working set mentre l'area esistente degrada.

Non pretendiamo zero weeds globali.

Pretendiamo che il **working set controllato** non venga progressivamente abbandonato alle weeds.

---

# 11. Workforce

La workforce deve seguire la superficie realmente lavorata.

Non assumere lavoratori anticipatamente per finanziare una futura espansione non ancora operativa.

Distinguere:

```text
livestock worker requirement
crop worker requirement
temporary operational requirement
```

Ricorda che gli Hands vengono rimossi a fine giornata.

Non considerarli capacità permanente.

---

# 12. Land expansion

In X1.8 Q2 NON deve essere comprato semplicemente perché esiste cash sufficiente.

La progressione desiderata è:

```text
Q1 core operativo
→ Cow scaling
→ working area crop densa
→ circa 5×5 produttivo/controllato
→ solo allora valutare Q2
```

Usa il costo reale del terreno.

Per X1.8 è preferibile comprare Q2 **troppo tardi piuttosto che troppo presto**.

Non dobbiamo ancora ottimizzare il timing economico del land purchase.

Vogliamo dimostrare la corretta sequenza architetturale.

# 14. Assert architetturali

Il replay seed 0 deve fallire esplicitamente se almeno uno di questi invariant viene violato.

## Core

```text
nessun livestock-core tile diventa PLANT
```

## Bootstrap

```text
nessuna normale crop expansion prima del completamento del core
```

È ammesso esclusivamente il Wheat minimo necessario al feed bootstrap, sempre fuori dal core.

## Cow survival

```text
Cow #1 non deve scappare entro Day 10
```

## Livestock progression

Deve essere possibile distinguere:

```text
1 → 2 → 3 → 4 active cows
```

oppure, se il quarto animale non viene ancora raggiunto entro 30 giorni, il report deve indicare esattamente quale gate lo impedisce.

Non considerare i semplici BUY come prova.

## Capacity

```text
active managed crop tiles <= capacity dei crop workers
```

Il livestock primary non conta automaticamente come crop worker.

## Working set

L'espansione non deve continuare mentre la capacità disponibile non riesce a mantenere l'area già attiva.

## Land

```text
unlocked != active working set
```

e nessuna assunzione di land cost fisso.
